# Audiobookshelf for Mere Mortals

An audiobook lives or dies by one small
mercy: remembering where you stopped.
**Audiobookshelf** is the open-source
server that provides it — a library for
audiobooks and podcasts that you run
yourself, on your own machine, with your
own files. It scans the folders you
already have, builds a tidy library from
the tags inside the files, streams to a
web player and to phone apps, and keeps
every listener's place — per person, per
book, per episode — on the server, so
you can stop on one device and resume on
another. This guide explains how it
works, how to install it, and where its
edges are.

The lab behind this guide ran the real
thing: **Audiobookshelf v2.37.1**, the
project's current release on build day,
installed from the project's own Linux
package and exercised through the same
**API** its web page and phone apps talk
to. Into it went invented books by
invented authors — audio synthesised on
the build machine, no commercial
recording anywhere — and one invented
podcast served from a fixture feed. The
lab proved the features the product is
loved for: a scan that read chapters and
tags correctly, streaming verified byte
for byte, listening progress that
persisted and survived a server restart,
a second user fenced out of a library
that wasn't theirs, and podcast episodes
downloaded from a feed and streamed
back. What the lab could not do, it did
not fake: there was no phone and no
container runtime on the bench, so the
apps and the Docker route are documented
from the project's own manual and
labelled as such. `criteria.md` keeps
the ledger of what was run and what was
only read.

## What this guide covers

- [**What Audiobookshelf is**](what-audiobookshelf-is.md) —
  the mental model: a library server, not
  a shop; your files stay ordinary files;
  progress is the point

  the one server program, its two data
  folders, the media folders it watches,
  and the ffmpeg tools it leans on

  the Docker route most people take, the
  Linux package the lab ran, and what
  each one leaves on your disk
- [**First admin and login**](first-admin-and-login.md) —
  the first account is the root account;
  what a login token is and who holds it

  pointing the server at a folder, what a
  scan reads, and how books are matched
- [**Chapters and metadata**](chapters-and-metadata.md) —
  where chapter lists come from — the
  files themselves, or one file per
  chapter — and what the online lookups
  can and cannot do

  the web player, streaming and seeking,
  direct play versus transcoding, and
  downloading for offline listening
- [**Progress and users**](progress-and-users.md) —
  the feature the product is loved for:
  per-person places, kept on the server;

  following a feed, downloading episodes,

- [**Limits**](limits.md) —
  what Audiobookshelf is not, stated

- [**Troubleshooting**](troubleshooting.md) —

- [**Glossary**](glossary.md) —

## The lab

Everything this guide claims was run,
the transcripts are kept in
`audiobookshelf-lab/transcripts/`:
server status and the web page (t00),
the first admin and login (t01),
libraries and scans (t02), items and
their chapters (t03), streaming and
range requests checked byte for byte
(t04), playback progress recorded and
read back (t05), the same progress
after a server restart (t06), the
second user's fencing (t07), the
podcast feed (t08), episode download
and streaming (t09), and the backup
file (t10). The fixture media is
regenerated by `examples/generate-fixtures.sh`;
the commands are collected in
`examples/commands.txt`, and the lab's
own notes in `examples/lab-notes.txt`.
